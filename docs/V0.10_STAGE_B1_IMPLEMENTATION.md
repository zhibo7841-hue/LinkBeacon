### Implementation and contract

Added under `feature/lanscan/src/main/java/com/networktoolbox/feature/lanscan/domain/recognition/`:

- `LanRecognition.kt`: closed semantic codes, categories, dimensions, source/field
  references, typed arguments, reported-platform values, result status and limitations.
- `LanRecognitionMapper.kt`: a pure Kotlin object with invocation-local accumulators.
  It has no Android, network transport, coroutine, clock, repository, database,
  HistoryRecorder, profile, ViewModel, localization or UI dependency.

`map(session, ipAddress, currentContext)` looks up a single device **inside** the
supplied completed scan. It checks a positive matching session generation, the
current network fingerprint and its consistency with the captured NetworkContext.
Unsupported/VPN/inactive, cancelled, invalidated or different-network sessions
return `NOT_CURRENT` with no hints. An absent/invalid/ambiguous target returns
`DEVICE_UNAVAILABLE`; the mapper never creates a discovered device.

Evidence is accepted from explicit PTR hostname provenance, mDNS records resolved
to that device's IPv4 address, and UPnP records with the captured generation and
network identity. Per-record times before scan start are ignored; post-discovery
enrichment times may be after scan completion. No new clock or made-up PTR time
is introduced. A multi-time conflict has no invented common observation time.

Every hint carries a stable code, evidence category, dimension, bounded typed
arguments and source-labelled field references. An opaque SHA-256 reference is
derived from permitted observation values and available time; it is scoped to
interpreting this input, not a persistent device identifier or matching key.
The result retains neither raw TXT maps nor their MAC/password/import-URL fields.
It does not translate or store finalized user-facing sentences; B1.1b will own
bilingual text binding under separate authorization.

The four categories are service observations, device-reported information, weak
name clues, and insufficient/comparably conflicting evidence. There is no hardware
confidence percentage or authenticated-device conclusion.

### Rules, counterexamples and limits

- Only normalized exact `_esphomelib._tcp` records interpret the allowed TXT keys
  `platform`, `board`, `friendly_name`, `version`. Case-insensitive exact platform
  values ESP32/ESP8266 remain **self reports**; RP2, LibreTiny and other values are
  retained as other reported platforms. `not-ESP32` is not classified as ESP32.
- Ordinary HTTP/IPP/SMB advertisements and port 6053 do not imply an ESP platform.
  Board alone, an UPnP model or a protocol device type cannot establish a chip.
- Explicit ESP32/ESP8266 tokens in PTR or actual mDNS instance names produce only
  weak clues. Incomplete substrings, negated tokens, generic `esp`, IP literals,
  Unicode lookalikes, unknown hostname provenance and address-derived mDNS
  hostnames do not invent an ESP/PTR assertion.
- Only comparable platform claims generate a conflict. Individual reports remain
  inspectable; names/aliases, manufacturer, protocol role and product model are
  separate dimensions. A weak name differing from a platform report is not a
  second authenticated platform claim.
- Duplicate normalized TXT keys suppress the affected field, even if their values
  agree. Oversized/unsafe values are rejected, not truncated into valid platform
  values. Control, formatting/bidirectional, line/paragraph separator and malformed
  surrogate characters cannot be stripped into an accepted claim. Safe Unicode
  descriptive text remains usable as plain data.
- Text is bounded to 128 UTF-16 code units (PTR hostname 255, service type 64,
  TXT key 64); at most 16 TXT attributes are considered for a target service.
  This is a stricter interpretation budget than parts of the collector, not a
  change to collection limits. Rejected data is signalled as a limitation.
- At most **32 hints** and **4 conflict values/references** are emitted per device.
  Bounded sorted accumulators retain a deterministic prefix and prioritize the
  conflict hint, with `OUTPUT_LIMIT_REACHED` rather than a completeness claim.
  Exact duplicate facts do not grow output. Different source/field references,
  parameters and times remain distinct unless the explicit output limit applies.
  Runtime is linear in supplied observations apart from the fixed-size sorted
  output; the mapper does not sort/copy an unbounded explanation collection.
- No candidate 64-instance admission limit is implemented. The NSD adapter,
  service catalog (HTTP/IPP/SMB), 4-second window, resolve cap, Executor, queues,
  host concurrency/timeouts/ports, PTR and SSDP/UPnP collection remain unchanged.

### Accuracy, conflict handling and isolation conclusions

- Service matching lowercases with `Locale.ROOT`, accepts the existing bare
  DNS-SD service form plus one optional terminal dot, then uses a complete match.
  Only exact `_esphomelib._tcp` interprets the four allowed TXT fields. Arbitrary
  domain suffixes, substrings and malformed service forms are not guessed into it.
- Platform classification uses exact ESP32/ESP8266 values, not Unicode-aware
  fuzzy matching; RP2 and other reported values remain `OTHER`. Platform and
  board/model/manufacturer are separate dimensions. A port, `not-ESP32`, generic
  `esp`, a saved custom name or a normal HTTP/IPP/SMB service cannot prove a chip.
- PTR and actual mDNS instance-name tokens remain weak clues. Address-derived
  mDNS hostnames are not original PTR/SRV identity evidence. Unsafe characters,
  lookalikes, combining marks, oversized values and ambiguous normalized TXT keys
  cannot be repaired into platform facts. Allowed Unicode descriptions remain data.
- Comparable platform values retained in multiple observations preserve a conflict
  and source references. Different names can be aliases; UPnP model vs mDNS
  platform is not an invented same-dimension conflict. Already lost collector
  conflicts cannot be recovered. Duplicate facts and input reordering do not change
  the semantic result, including when the output limit applies.
- The caller must supply a current positive generation and network context; the
  mapper checks completed state, supported active network, VPN absence, captured
  fingerprint consistency and exact unambiguous device membership. UPnP also has
  per-record generation/network/time checks; mDNS uses address/time checks.
- Production dependencies and call sites confirm no transport, Android permission,
  database, profile or History collaborator. There is still no production caller.
  Input observations, MAC/UDN matching, Custom Name, Device Type, Notes, Favorite,
  WoL, First Seen, Last Seen, serialized History and all current filter sets are
  unchanged. Repeated mapping starts no scan, adds no network-context reads and
  writes no History; one fake completed scan still writes exactly one History row.

### Resource review and limitations

The output remains bounded to 32 hints and four comparable conflict values and
references. Each accepted text field is at most 128 UTF-16 code units (PTR 255,
service/key 64); TXT maps over 16 attributes are rejected. Bounded sorted maps
retain deterministic representatives rather than sorting/copying the entire
input. The extra evidence-scope digest is computed once per invocation. Traversal
is linear in supplied observations/text, with fixed-size output accumulators;
input itself is caller-owned and is not given a new admission cap here. This is
source-level resource review, not a real-device CPU/memory benchmark.

`OUTPUT_LIMIT_REACHED` explicitly reports incomplete output; lower-priority facts
can be omitted under load. The precedence fix cannot promise that every platform
or service survives more than 32 distinct high-priority facts. `NO_USABLE_...`
means no additional mapper evidence, not offline, not no observed device name,
and not a replacement for Stage A identified/unknown logic.

PTR has no per-record generation/time and mDNS has no per-record generation.
The existing guarded session remains the provenance boundary; hashing its scope
does not authenticate a record incorrectly reinserted upstream. Existing mDNS
same-name deduplication and UPnP scalar merging can discard conflict data. These
limitations are disclosed, not addressed by widening the collection layer.

The default catalog is still HTTP/IPP/SMB only: no `_esphomelib._tcp` discovery,
fourth type, new 64-instance admission budget, queue/concurrency change or new
network operation. The four-second mDNS window and resolve cap of two, host
discovery parameters, PTR/UPnP collection and long-lived NSD Executor are unchanged.
