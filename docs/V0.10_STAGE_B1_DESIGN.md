### 1.1 发现与补充的时序

```text
用户开始扫描 → 既有主机发现 → Completed → 一条 LAN_SCAN History
                                    └→ PTR / mDNS / UPnP 并行补充
                                        → 当前 LanDevice observations
                                        → identity / presentation
```

现有主机参数为 Reachability **500 ms**、TCP **250 ms**、worker 上限/默认 **32**；
fallback 顺序 **80 / 443 / 22 / 445 / 53 / 9100**，成功即停止该地址的后续端口。
TCP 只有 CONNECT SUCCESS 是独立发现证据，REFUSED / TIMEOUT / UNREACHABLE 不算。
范围、网络指纹、取消、VPN/Cellular 限制全部不因 B1 改变。

`LanScanHistorySerializer` 当前 schemaVersion=1 保存范围、进度、耗时、IP、
角色、延迟与 discoveryMethods，不保存后续身份补充；不得声称历史可重放完整 TXT。
补充不新增 History，也不重写已保存扫描快照。

UPnP 的既有安全预算为 SSDP 默认 3,000 ms、最多 32 个描述获取、同时获取≤2、
HTTP connect/read 分别 1,800/2,200 ms、XML≤384 KiB / 深度≤64 / 服务≤32。
LOCATION 仅允许响应者自身的 literal HTTP(S) 地址，不跟随重定向；拒绝 DTD 并隔离
外部实体。不因识别需求放宽这些校验；它们是受限补充，不是通用网页爬取。

### 1.2 名称、服务与信息损失

当前 displayName 顺序为：有效 UPnP friendlyName → mDNS serviceName →
mDNS hostname → hostName（通常为系统反向解析）→ IP fallback。
同一来源候选经过排序/去重后取首个；上层再应用用户 Custom Name。
厂商、modelName/modelNumber/modelDescription、deviceType 目前只来自 UPnP。
`LanIdentityService` 保留 mDNS/UPnP 服务条目，但现有详情没有完整展示这些条目。

已采集但尚未充分用于解释：

- `LanMdnsObservation.txtAttributes`、serviceType/port、IPv4/IPv6、observedAt。
  TXT 不参与当前 ESP 识别、MAC 匹配或自动 Device Type；不应直接全量展示。
- UPnP 厂商/型号已用于摘要；UDN 用于既有匹配。deviceType、services、SERVER、
  manufacturerURL、presentationURL 等存在观察中，但不是硬件型号验证。
  URL 不自动打开/抓取；SERVER 不是可信操作系统判定。
- `LanSourcedValue` 已提供来源，但 `DeviceDetailPresentation` 的 vendor/model 等
  多为 String，且可能从 saved profile 回退；新展示不能把历史值标成当前新观察。

不能假定观察是完整原始记录：

1. mDNS 同一 `(serviceName, serviceType)` 在 Session 内先去重；enricher 对
   service/address 首次接受，且只关联响应地址中**第一个**已发现 IPv4。
   ViewModel 每设备最多保留 16 条 mDNS 观察。相同实例名碰撞、同实例更新或多地址
   可能被合并/遗漏，现有模型不保证还原所有冲突。不能仅按名称合并两台设备。
2. UPnP 每设备最多 8 条观察，但 enricher 在回传前已按源 IP 合并多个描述，
   标量取 first non-null；解析器忽略嵌入设备元数据。已丢失的同源冲突不能由
   presentation 凭空恢复。Aggregator 的确定性不等于整个采集链完整、顺序无关。
3. 当前 mDNS `hostname` 来自 `getHost()?.hostName`，不是专用 NSD `getHostname()`；
   它可能是 InetAddress 缓存名或系统解析结果，不应标为已读取原始 SRV target。
   这一路还可能在 callback executor 上触发系统名称查询，是后续性能审计点。
4. PTR 的 1,500 ms 是 UI 可见期限，不是底层 DNS 调用硬超时。同代迟到成功仍可能补名；
   停止/换网后的旧代结果应被丢弃。不能宣传“所有 PTR 在 1.5 秒内物理终止”。
5. 当前主机发现没有 MAC 采集器；MAC 字段可为空，不能从 TXT 或 IP 补造。

### 1.3 Stage A 筛选与 Saved Profile 的实际语义

两个列表复用 `DeviceCenterPresentation.hasObservedIdentity`：

- 只考察 `observedThisScan` 的设备；本机/网关角色直接满足条件。
- 其他设备的非 IP fallback displayName、hostname、manufacturer、modelName、
  modelNumber 或 deviceType 任一存在即可。**modelDescription 单独存在、服务列表单独
  存在并不在该谓词中。**有效 PTR/mDNS 名称可以使设备进入“已识别”。
- 未观察到的持久化资料既不算本轮已识别，也不算本轮身份未知；旧厂商、手工名称、
  收藏和手工类型不把一个当前未知观察升级为已识别。查询/筛选是本地操作，不触发扫描。

因此“已识别”在现有产品中是**有可用观察身份信息/角色**，不是“认证了芯片”。
B1 不把它重新定义成认证等级，也不把新 `possible ESP32` 提示塞回 hostName/model/type
来改变计数。基线已因真实名称而计入的设备，也不应为了弱线索分类被移出。

Saved Profile 按当前 `LanNetworkScope` 匹配；MAC/协议身份优先，冲突或歧义不关联，
同 scope 同 IP 只能构成 WeakCompatibilityMatch。关联展示可以使用弱匹配资料，
但 ViewModel 自动 `updateLastObserved` 仅接受 StrongMatch。
补充沿用 `device.lastSeen`（发现阶段时间），不是用 TXT 到达时间刷新 Last Seen。
`userDeviceType` 优先于 `detectedDeviceType`；自动更新接口不写 Custom Name、Notes、
Favorite、WoL。当前 UDN 为自报协议标识，内部“强”关联仍不能防止主动伪造。

## 2. 识别证据与可信程度

建议用**证据类别**而非百分比置信度。下面的“确认”只确认 App 收到了对应观察，
并未认证发送者或硬件；本地网络也不是可信输入边界。

| 类别 | 例子 | 允许表述 | 禁止升级 |
| --- | --- | --- | --- |
| 已观察服务 | 在匹配的当前设备地址上解析到 `_esphomelib._tcp` | `已观察到 ESPHome 服务公告 · mDNS` | 不等于 API 可连接/鉴权通过，不等于 ESP 芯片 |
| 设备自行声明 | 相应服务 TXT 的 `platform=ESP32`、`board=...`；UPnP manufacturer/model | `设备报告的平台：ESP32（mDNS TXT）`、`设备报告的厂商（UPnP）` | 不等于已验证硬件/制造商、不可写为正式 Device Type |
| 弱名称线索 | 系统反向名称或实例名含明确 `esp32` / `esp8266` token | `名称含 ESP32 线索，硬件未确认 · PTR` | 不能写成“已识别 ESP32”，不能推进身份匹配/Last Seen |
| 不足 / 冲突 | 无值、无发现协议、两个可比较的平台声明互相矛盾 | `暂无可用识别信息` / `平台声明不一致`，保留各来源 | 不选一个猜测型号，不判离线、恶意或扫描失败 |

IP、网段、延迟、80/443/6053 等普通端口、名字相似、用户自定义名、MAC 厂商猜测
都不能直接确定 ESP 型号。未主动验证的 advertised port 只显示“公告端口”。
多个自报来源一致也只是“声明一致”，不自动提升为认证硬件。
DNS-SD 对真实性有单独的安全要求；当前链路未提供硬件认证。
[RFC 6763 §15](https://www.rfc-editor.org/rfc/rfc6763.html#section-15)

历史 profile 缺少可靠来源时标“上次保存的信息 / 来源未记录”，不要推测来源。

## 4. ESP32 / ESP8266 策略

### 4.1 官方资料与可用性边界

核对 ESPHome **2026.9.0 tag**：native API 条件分支注册 `_esphomelib._tcp`，
并按构建条件写入 platform、board 等 TXT；平台也包括 RP2、LibreTiny、nRF52，
不能把 ESPHome 当作 ESP32 同义词。无 API 时 `_http` 分支提供的设备信息不同，
不保证 platform/board；fallback `_http` 公告本身甚至不证明实际 Web 服务可访问。
[固定版本源码](https://raw.githubusercontent.com/esphome/esphome/2026.9.0/esphome/components/mdns/mdns_component.cpp)

mDNS 可被固件配置关闭，也可广播自定义服务/TXT，因此没有公告不排除 ESP 硬件，
有公告也不能认证它。固件版本、组件开关、网络隔离都会影响覆盖。
[ESPHome mDNS 文档](https://esphome.io/components/mdns/)
官方 RP2 平台支持 Pico W 等设备，可用于非 ESP 硬件负例。
[ESPHome RP2 文档](https://esphome.io/components/rp2/)

### 4.2 提议规则（不是当前实现）

1. **先验证归属**：只处理当前 scan/network/generation 内已经通过原有发现规则进入
   结果的设备。接受经过既有清理/上限处理的 observation，不按名字跨 IP 或跨网络关联。
2. **服务规则**：规范化服务类型大小写/结尾点后，精确匹配 `_esphomelib._tcp`。
   不以任意字符串包含 `esp`、端口 6053 或 HTTP 服务名代替。
3. **平台规则**：仅在该服务的 TXT 上解释允许的 `platform` key，trim 后对
   `ESP32` / `ESP8266` 作严格大小写无关值匹配；其他值保留为设备报告的其他/未知平台，
   不通过 substring 把 `not-ESP32` 等映射成 ESP32。未来新增枚举需有证据与测试。
4. **board / friendly_name / version**：作为有界、来源明确的设备报告文本；
   `board` 单独存在不反推芯片，不承诺商业产品型号。friendly_name 只是观察字段，
   不写入 Custom Name；本轮建议也不改变既有主标题选择算法。
5. **名称线索**：PTR、实际 mDNS 实例名可以匹配有边界的 ESP32/ESP8266 token，
   如 `esp32-sensor`；`desp32thing`、数字 IP、泛用 `esp`、保存的手工名不触发。
   仅生成弱线索；更具体的自报平台与名字矛盾时保留名称而不猜真实硬件。
6. **UPnP**：原样有界展示 manufacturer/model/description 的设备声明；
   其中写着 Espressif 或 ESP32 也不升级到认证。`Basic:1`、`MediaRenderer:1` 等
   deviceType 是协议角色，不能推出芯片。无需新增关键词→Device Type 自动写入表。
7. **冲突**：比较同一维度的明确声明；两个 ESPHome 服务报告 ESP32 与 ESP8266
   则撤下单一平台结论，列出两条证据。厂商与平台、芯片与整机型号不是同一维度；
   未有规则支持时只并列展示，不制造冲突。名称不同通常只是别名。
8. **不足**：只看到泛用 `_http`、`_ipp`、`_smb` 或普通 TCP 成功，只报告服务或发现
   依据。无 mDNS 的 ESP 仍可由现有主机发现进入列表，但可能保持身份未知。

反过来，即使收到 ESPHome 公告，若主机不响应现有可达性检测且只开放 fallback
集合之外的端口，它仍可能未进入发现列表；当前补充器会忽略该地址。增加第四服务
不是解决所有 ESP 漏检的方案，本设计不因此增加端口或把服务公告提升为在线证据。

建议首阶段仅解释 `platform`、`board`、`friendly_name`、`version` 的允许字段。
TXT `mac` 不注入 `LanDevice.macAddress`、匹配器或 WoL；忽略 project/import URL
等其他字段的识别作用，不发起 API 握手、Web 抓取或进一步探测。
TXT key 规范化需保留大小写冲突检查，出现重复规范化键时不采用“最后一个赢”。
DNS-SD 的 key/value 语义与服务类型相关，不能把所有服务的同名 key 解释成 ESPHome。
[RFC 6763 §6.4–6.5](https://www.rfc-editor.org/rfc/rfc6763.html#section-6.4)

上述规则只是对可观察字段的解释，**不是设备认证、服务指纹扫描或覆盖率保证**。
部分声明可能已被当前去重/合并阶段丢弃，只对实际保留的冲突作结论。

## 5. mDNS 扩展可行性与风险

### 5.1 当前边界与 Android 分支

| 项目 | 当前实现 |
| --- | --- |
| 服务目录 | `_http._tcp`、`_ipp._tcp`、`_smb._tcp` |
| 类型数量 | `MdnsDiscoveryRequest` default / hard cap 均为 3；直接加第四种会被 require 拒绝 |
| 观察窗口 | 共用 4,000 ms；不是每类型四秒轮询 |
| resolve | `Semaphore(2)`；每个首次发现实例启动一个等待 permit 的 coroutine |
| callback Executor | `AndroidMdnsDiscovery` 实例级单线程 Executor，Hilt Singleton 注入；Session.stop 不 shutdown |
| 清理 | NEW / STARTED / STOPPING / STOPPED / FAILED；listener 幂等停止；MulticastLock 释放；异常隔离；generation/state 拒收迟到事件 |
| 内容上限 | TXT 16 项、key 64 字符、value 256 字符、合计 1,024 字符；不等同于 DNS 报文长度；非法 UTF-8 不作为文本 |
| 归属 | resolved IPv4 必须已在结果中；网络/代际核对；IPv6 仅附带数据，不新增 IPv6 discovery |

代码 API 31/32 使用旧 discover/resolve overload，无指定 Network 的 discovery 调用；
API 33+ 使用 Network/Executor，并拒绝已知不同 Network 的解析结果；
API 34+ 读多地址及调用 stopServiceResolution，较旧版本只停止接收/取消应用等待。
因此不能保证旧系统的 framework resolve 已物理结束，也不能把应用附加的
networkIdentity 当作 framework 在 API 31 返回的链路证明。

官方接口确认：Network/Executor overload 为 API 33（也有扩展版本），
stopServiceResolution 为 API 34 / T extension 7；旧 resolve 在 API 34 被弃用，
一次返回可能不完整或马上过时。当前实现仍使用一次性解析；B1 不顺带切换长时订阅 API。
多播锁需按当前 SDK/扩展版本分支保留。
[Android NsdManager](https://developer.android.com/reference/android/net/nsd/NsdManager)

官方 `getHostname()` 为 API 36 / T extension 17，而当前 adapter 未调用；
`getAttributes()` 只有 resolved service 的值才有效。新展示应准确说明当前兼容字段，
不得无条件调用新 API 或承诺跨系统都有 SRV hostname。
[Android NsdServiceInfo](https://developer.android.com/reference/android/net/nsd/NsdServiceInfo)

### 5.2 建议选择与批准门槛

| 选择 | 取舍 | 建议 |
| --- | --- | --- |
| 保持三类型，仅解释现有观察 | 不增加 NSD 负载；无法稳定获得 ESPHome API TXT | 可先完成纯 mapper/展示，但不能称 ESP 专项验收完成 |
| 保留三类型并加入 `_esphomelib._tcp` | 请求上限/default 集中改为 4；增加一组 discovery 注册和广播响应量 | **建议单独审批后实施**；窗口仍 4 s、resolve 仍 2 |
| 替换旧类型或按时间轮转 | 丢失已有覆盖或压缩单类型有效窗口；延长时间则改变预算 | 不推荐，不能未经确认实施 |

不是增加一种全新扫描协议，而是既有 NSD 的有限服务目录扩展；仍须单独批准、
实测和隐私数据项复核。不得扩大到服务通配枚举、全服务目录、MQTT/Matter/ARP/OUI，
不加权限、不更改 host probe 参数或 discovery-positive 规则。

### 5.3 不能忽略的资源与归属风险

- **2 个 active resolve 不代表总任务数有硬上限。**当前每个独特服务 launch 一个
  coroutine，seenServices/等待 permit 集合没有明确总数量 cap。三改四后热点网络或
  伪造公告可能增加排队、内存及 callback backlog；四秒期限不等于数量边界。
  建议在获批的 B1.2 adapter 安全项中先审查并加入独立的有界 admission/queue，
  例如全会话最多接纳 64 个唯一待解析/已解析实例、同时 active≤2；64 是待实测的
  **提议值**，不是现有能力或无损覆盖承诺。超额只标信息不完整，不更改设备在线状态。
  若此配套不获批，保留三类型并回报风险，不默认扩大目录。
- 四种 discovery 共用同一个会话窗口和长期 Executor；停止、超时、离页、换网、
  重复 stop、三/四类型同步结束均不得关闭该 Executor。framework 晚到任务必须能被
  接受，再由 Session/generation 忽略；不能只靠业务 callback 的 try/catch 掩盖派发异常。
- API 31 的链路归属和同名去重有上述缺口；不同地址的同名服务不能拿前一设备 TXT
  补后一台，更不能据名字创建 Saved Profile 匹配。对不能可靠关联的证据宁可不展示。
- 回调中的 `InetAddress.hostName`、阻塞 PTR、SSDP 收包集合都是需测量的成本；
  现有 SSDP 是时间/单包有界，不是响应数量硬封顶。不能宣称全链路已抗任意公告洪泛。
  本轮只记录，不改这些实现；B1.2 以 mDNS 队列与实测为独立安全门槛，其他缺口另行审批。
- 未启用 mDNS、只启用其他类型、设备休眠、多播隔离/代理、NSD 缓存、resolve 失败、
  窗口外响应都可能补充不到。4 s 内无公告不是设备离线或非 ESP 的证据。
- 先前 Task 039-A/B 的生命周期和 Executor 修复是约束，不可回退。不能靠加长
  窗口、反复重试、无限注册或扫描后后台运行来掩盖漏检。

## 6. 数据设计及用户资料保护

建议新增**纯、无副作用的 transient presentation/domain 映射**，沿用 Stage B
总设计的 `LanRecognitionMapper` 方向，不新建 identity repository：

```text
当前已清理的 LanDevice observations + scan 上下文
  → LanRecognitionMapper
  → RecognitionPresentation（证据行 / 提示 / 冲突 / 局限）
  → LAN Scanner 与 Device Detail 共用

既有 identity / Saved Profile matcher / Last Seen / History 路径不接收 Recognition 输出
```

建议每条结果至少包含：稳定 code、类别（服务观察/自报/弱线索/冲突）、维度、
source、指向本次观察的 evidenceRef、可展示的有界 value、可用时的 observedAt。
上下文用既有 generation/scope，不生成新的持久设备 ID。
EN/zh 由 code/typed arguments 映射，原始协议值不翻译；不用散落在 Composable 的
字符串识别，也不引入百分比“置信评分”。相同输入得到相同输出，排序与 callback
到达次序无关；这一保证只覆盖 mapper 输入内实际保留的观察。

约束：

1. **资料只读**：新 mapper 不持有 repository，不写任何 profile；用户编辑、Favorite
   与 WoL 各自流程不变。network-sourced type 与 userDeviceType 不混写。
2. **身份分离**：名称提示、TXT platform/board/mac、服务名不传入 matcher；不新增
   强匹配方式、不改 UDN/MAC/scoped-IP 优先级、不修复或迁移旧 profile。
3. **时间分离**：observedAt 只描述补充记录，不代替 discovery lastSeen；同输入增加
   hint 前后 profile 的 firstSeenAt/lastSeenAt 不变；不得调用 updateLastObserved 作为
   “识别成功”副作用。既有 StrongMatch 更新保留原发现时间和现有流程。
4. **筛选分离**：纯 mapper 输出前后 identified/unknown 集合必须相同。第四种服务
   可能带来一个新的、真实的有效 mDNS 名称，现有谓词会据此计入已识别；这属于新增
   观察覆盖，不是平台认证。B1.2 必须由维护者明确接受此效果并在 UI 保留筛选依据。
   只有 platform hint、没有符合既有谓词的身份信息时不能强制变为已识别。
5. **保留冲突**：不覆写输入。输出保留可比较维度的相异值及来源，不以 UPnP 优先级
   当真伪裁判。无法恢复已被 enricher 合并的值时说明限制，不编造完整冲突日志。
6. **安全输入**：仅 plain text，不解释 HTML/Markdown/URL；防控制字符、双向文本
   干扰、异常长度、非法 UTF-8、规范化键冲突。当前清理不等于完整 Unicode 安全处理；
   新层可拒绝不安全候选，不能改写原证据为另一个合法平台。超限/缺失则不推断。
7. **留存最小化**：新识别提示仅限当前会话；不增加 Room/History schema 或 raw TXT
   落盘、日志上传、跨会话自动重判。历史资料无 current evidence 时不恢复“当前 ESP”。
   现有持久化名称/厂商/型号流程保持，不声称所有既有身份信息从不持久化。
8. **状态隔离**：停止/离页/新扫描/换网后旧结果不能更新新页面或新资料。
   展示、语言切换、筛选、展开详情只读，不重启任何检测。
