## 3. B1 — evidence-based device recognition

### 3.1 Existing execution and safety boundaries

`LanScannerViewModel -> existing discovery -> reverse DNS / mDNS / UPnP
enrichment -> LanDevice observations -> identity/presentation`

- Host discovery is independent of identity enrichment: 500 ms reachability,
  250 ms TCP, host concurrency 32, existing ports 80/443/22/445/53/9100 and
  TCP CONNECT SUCCESS-only evidence. Keep range, cancellation, VPN/cellular,
  generation, scope and online/non-discovery semantics unchanged.
- mDNS currently searches exactly `_http._tcp`, `_ipp._tcp`, `_smb._tcp`.
  Request default/hard service-type cap is **3**, window **4,000 ms**, Android
  resolution cap **2**. App-adapter-owned callback Executor remains alive
  beyond sessions; idempotent stop/generation guards must survive all changes.
- API 31/32 uses the older discovery/resolve overloads; API 33+ can use the
  existing Network/Executor overload. Address/hostname handling has additional
  SDK-extension/version checks. Do not blindly replace these with a newer
  API that the minimum-supported device cannot call. [NSD API reference](https://developer.android.com/reference/android/net/nsd/NsdManager)
- TXT is already bounded to 16 attributes, 64-character keys, 256-character
  values and 1,024 total characters in the Android adapter.
- Reverse DNS uses `InetAddress.canonicalHostName` off Main. Four workers and
  a 1,500 ms visible deadline do **not** make its blocking resolver physically
  cancellable; retain bounded occupied workers and reject late generations.
- SSDP uses `ssdp:all`, a 3,000 ms discovery window, at most 32 description
  fetches with two concurrent fetches. Keep responder-literal LOCATION
  validation, no redirects, XML/XXE protections, 384 KiB body cap and existing
  socket/time limits. This is not a general HTTP fetch surface.

### 3.2 Recommended design

Start with a pure `LanRecognitionMapper` over **current** sanitized observations.
Its proposed output is a small list of `DeviceRecognitionHint(code, source,
evidenceReference, confidence, observedText)` attached to presentation, not a
second identity repository. Stable message codes are localized in EN/zh.

| Observation | Allowed explanation | Must not claim |
| --- | --- | --- |
| PTR/instance name contains `esp32` or `esp8266` | Weak name-based clue, explicitly qualified | Proven chip/vendor/model, stable identity or online proof |
| `_esphomelib._tcp` advertisement | Service advertises ESPHome-compatible API | Every ESPHome device is an ESP32, or every ESP32 advertises this service |
| That service includes bounded `platform=ESP32/ESP8266`, `board`, `friendly_name` | Device-reported platform/board/name with mDNS source | Authenticated hardware identity or permission to overwrite a user name/type |
| UPnP manufacturer/model/deviceType | Device-reported metadata with source | Verified hardware/vendor or vulnerability conclusion |
| No usable observation / conflicting claims | Unknown / conflicting evidence with explanation | Scan failure, offline status, invented best-match model |

ESPHome's tagged 2026.9.0 source advertises this service and optional device
information under compile-time conditions; other platforms are also supported.
This is evidence for a candidate recognizer, not universal coverage.
[ESPHome source](https://raw.githubusercontent.com/esphome/esphome/2026.9.0/esphome/components/mdns/mdns_component.cpp)

Only merge an observation into a host already found in the captured scan and
matching IPv4/network/generation. Preserve existing MAC/protocol/network-IP
matching, user-selected Device Type, Custom Name, Notes, Favorite and WoL.
TXT `mac` must not become a trusted MAC or trigger identity promotion. Do not
learn arbitrary TXT secrets/project-import URLs or fetch them. Existing raw
observations stay available; conflicting claims are not erased by callback order.
Hint-only recognition does not refresh Last Seen or make a persisted unseen
profile count as a current identified discovery. Reuse the Stage A observed
identity/filter predicates; do not silently redefine their counts.

### 3.3 Coverage extension requiring confirmation

Appending a fourth type currently fails request validation. Recommended small
follow-up, **only after approval**: add `_esphomelib._tcp`, centrally change
service discovery cap/default from 3 to 4, retain all original types, the
4-second window, resolve cap 2 and long-lived Executor. Validate measured
callback/resource behavior before accepting this increase. Do not add wildcard
enumeration, `_arduino`, Matter, MQTT discovery or a broad type catalog as a
side effect. If the increase is not acceptable, return for an alternative
bounded scheduling decision rather than dropping an old type or extending time.

### 3.4 Modules, risk, tests and acceptance

- Change later: `feature:lanscan/domain`, `domain/model` only if a transient
  hint value is needed, `presentation`, EN/zh resources/tests; `app/di` only
  if configuration injection needs wiring. Android adapter/config changes
  belong to the separately reviewed coverage slice. No Room schema change.
- Main risks: spoofed TXT/XML, name collisions, false hardware certainty,
  cross-network contamination, NSD late callbacks/Executor rejection, slow
  blocking PTR, resource increases on API 31 and API 36.
- Unit fixtures: ESP32, ESP8266, non-ESP ESPHome, same-name unrelated hosts,
  absent/malformed/oversized TXT, conflicting sources and shuffled callback
  order; generic HTTP must not identify an ESP device. Preserve user profile,
  identity, filtered counts and Last Seen assertions.
- Lifecycle tests: repeated start/stop, cancellation, timeout, network switch,
  late discovery/resolve, Executor acceptance after close and no result leakage.
  Reuse `MdnsDiscoveryTest`, `AndroidMdnsDiscoveryExecutorTest`, UPnP/PTR and
  identity suites instead of replacing them with new superficial mocks.
- Device acceptance: controlled ESP32 + ESP8266, a non-ESP device and a device
  with discovery disabled on Android 12/16, plus denied/restricted LAN access.
  Record firmware, observed source and unknown cases. If boards are absent,
  mark hardware recognition Not Tested; fixtures are not hardware acceptance.
- Pass: evidence-backed, reversible hints; unchanged discovery results for
  unchanged host evidence, no added online claims/profile mutation and no crash
  after enrichment completes. No claim of complete smart-home recognition.

## 4. B2 — Wi-Fi explanations, not invented RF measurement

Task 135's maintainer-confirmed **professional-data-first** product principle
and [Wi-Fi field/rule review specification](V0.10_STAGE_B_WIFI_DESIGN.md) refine
this section's presentation proposal. Keep key observations directly inspectable;
status qualifiers stay visible while educational explanations expand on demand.
That specification audits the Work report E01–E13 against actual code, including
the absence of current-connection Channel Width. Its evidence-first presentation
hierarchy refines earlier summary-first placement suggestions here; no Runtime
is implemented.

### 4.1 Current source and reuse

`WifiAnalyzerScreen -> WifiAnalyzerViewModel -> WifiAnalyzerUseCase ->
WifiScanRepository -> AndroidWifiAnalyzerPlatform` remains the only Analyzer
observation/refresh path; Home still uses the shared `NetworkRepository`.

`WifiSignalClassifier` already maps valid -126..-1 dBm to EXCELLENT (-50..-1),
GOOD (-65..-51), FAIR (-75..-66), WEAK (remaining valid readings), else UNKNOWN.
This is a receive-signal display policy, not an Internet-quality algorithm.
`WifiFreshness` combines monotonic timestamps and request/callback evidence.
Channel summaries count observed AP rows by band/channel and ignore AP-search
text. No channel utilization, interference, throughput or latency is measured.

### 4.2 Proposed presentation-only addition

Introduce a pure `WifiExplanationMapper(snapshot, selectedBand)` producing
bounded explanation codes and typed arguments. Reuse existing classifier,
freshness, permission and channel summaries; no duplicate thresholds.

- Weak signal: "Received Wi-Fi signal is weak. Moving closer to the access
  point may help. This does not measure Internet speed or packet loss."
- Many observed APs: "Several access points were observed on this channel;
  their count does not measure airtime use or interference." State whether
  observations are cached; do not add a numeric congestion score.
- Cached/restricted: explain observation age, permission, Location Services,
  Wi-Fi-off or platform throttling as separate facts. A selected 6 GHz band
  with no rows means not observed, not unsupported hardware or an empty band.
- Current-link RSSI and last scan RSSI are different observations. Link speed
  is negotiated link information, not measured application throughput.
- Show a few relevant explanations, expandable limits and existing manual
  Refresh/settings actions. No automatic Ping, automatic scan, Best Channel,
  distance estimate, antenna advice asserted as fact or new chart/score.

### 4.3 Android 12–16 boundaries

For the existing target/API path, nearby scans require Fine Location and
enabled Location Services; Coarse-only is insufficient. Current source uses
Fine/Coarse, Wi-Fi read/change permissions and **not** NEARBY_WIFI_DEVICES as
a substitute. Foreground scan requests can be throttled; a callback or
accepted request does not establish fresh results. Keep permission requests
in the Activity and do not alter system throttling for acceptance.
[Android scan restrictions](https://developer.android.com/develop/connectivity/wifi/wifi-scan)

LAN local-network protection is a separate concern from Wi-Fi scan permission:
Android 16's opt-in restrictions affect NSD/local sockets. Add a separately
identified restricted-environment test where feasible; do not silently opt in
or add permissions in this task. API/SDK-extension eligibility must be checked
at implementation time, not inferred from current docs advertising newer APIs.
[Android local-network protection](https://developer.android.com/privacy-and-security/local-network-permission)

### 4.4 Modules, risks, tests and acceptance

- Later edits: `feature:wifi/presentation`, `ui` and EN/zh resources/tests.
  Use existing `core:network/wifi` values; change platform collection only if
  a reproducible missing fact is separately demonstrated. No new permission,
  persistent SSID/BSSID, History, Device Center merge or analyzer integration.
- Risks: turning a signal grade into a health score; stale data presented as
  current; inaccurate band/hardware claims; inaccessible or overlong prose.
- Unit matrix: every signal boundary/invalid RSSI, current-vs-scanned readings,
  fresh/cached/unknown/permission-denied states, missing APs, mesh same-SSID
  rows, 2.4/5/6 GHz, channel counts unaffected by search and null radio data.
- UI/device: EN/zh/system locale, light/dark, large type, TalkBack; Android
  12/16 denied/approximate/Fine, Location-off, cached and manual refresh.
  Assert explanation changes/navigation/recreation trigger **zero extra scan
  requests**, and that no observation is persisted or uploaded.
- Pass: explanations can be traced to a snapshot field; no invented RF or
  Internet conclusion, no observer/permission/refresh behavior regression.

## 5. B3 — RDAP-first domain registration lookup

### 5.1 Product and architecture proposal

Registration information is not DNS, ownership verification, target
reachability or proof of whether a domain can be purchased. Initial UI is
one domain input and explicit Lookup, with source/service/time and qualified
missing/redacted fields. No bulk mode, automatic refresh or background query.

Proposed chain:

```text
feature:registration ViewModel / LookupDomainRegistrationUseCase
  -> DomainNameNormalizer
  -> RdapBootstrapResolver + endpoint policy
  -> RdapClient (cancellable bounded JSON body adapter)
  -> RdapResponseParser / pure registration mapping
  -> DomainRegistrationResult -> localized UI
```

Proposed placement: pure request/result/status/policy models in
`core:network/registration`; Android IDNA/DNS/HTTP adapters beneath it; a small
`feature:registration` presentation module and app DI/Tools navigation wiring.
Do not embed this into DNS Lookup or Automatic Diagnosis. Nothing is created
in Task 134. No History/table migration or automatic report export is proposed
for this first slice; any such addition requires its own confirmed task.

### 5.2 Input and authoritative endpoint selection

1. Accept an explicit DNS domain, not a URL. Reject scheme, credentials, path,
   query/fragment, port, IP literals, wildcard/underscore, empty labels,
   control characters and single-label/local names. Trim outer whitespace;
   normalize one optional trailing root dot and case. Enforce ASCII label
   length 1..63 and full name <=253 after IDNA; reject mapping errors.
2. Recommend platform ICU UTS #46 nontransitional ASCII conversion with STD3,
   BiDi/ContextJ checks, behind an interface. ICU IDNA exists before minSdk31;
   test mappings on API31/36 because platform Unicode data differs. Preserve
   displayed Unicode and queried A-label together; do not claim existing
   `java.net.IDN` DNS normalization is identical to this policy.
   [Android IDNA](https://developer.android.com/reference/android/icu/text/IDNA)
3. Use the IANA DNS bootstrap and label-wise longest-suffix match to select
   the authoritative RDAP base. Append the exact normalized domain using a
   URL builder. Do not choose an arbitrary commercial aggregation endpoint,
   scrape a website or hardcode a single registry for all TLDs.
   [Bootstrap specification](https://www.rfc-editor.org/rfc/rfc9224.html)
4. Recommended bootstrap strategy: ship a reviewed dated snapshot; check for
   a bounded HTTPS refresh only on explicit Lookup, with an age-labelled
   last-known-valid cache. No launch-time job or queried-domain cache. Confirm
   licensing/update provenance, TTL and invalid-update handling before coding.
   The [actual IANA registry](https://data.iana.org/rdap/dns.json) includes
   HTTP-only entries; **do not silently upgrade their URL, downgrade security
   or imply coverage**. Initial HTTPS-only policy reports unsupported service.
5. A bootstrap suffix is not an eTLD+1 calculation. Do not silently turn
   `a.b.example.co.uk` into the last two labels or send multiple parent queries.
   An exact-name 404 can suggest checking the registrable-domain input; it is
   not a universal "domain unregistered" conclusion. A PSL-backed parent
   helper needs a separately reviewed data/update policy.

### 5.3 HTTP, cancellation, errors and data model

Reuse installed OkHttp, system TLS trust and explicit `Call.cancel()` patterns.
Add a body-reading `RdapClient` adapter; **do not alter the existing website
headers-only `HttpProbe` contract** or run Website Diagnostics to fetch RDAP.
Use GET with `Accept: application/rdap+json`, no cookies/account/auth headers,
no automatic retries or redirects. Do not fetch arbitrary response links,
registrar contacts, images or `related` URLs. Retain source provenance.

Suggested **central config, pending confirmation**:

| Budget | Proposed value/policy |
| --- | --- |
| User lookup concurrency | 1, single-flight |
| End-to-end deadline | 20 s, includes bootstrap, DNS, connection, body and parsing |
| Connect / read wait | 3 s / 5 s, never exceeding remaining total budget |
| RDAP requests | At most 4 HTTP exchanges, shared across redirects/fallback |
| Redirect / alternative base | At most 3 redirects; at most one alternative trusted base within the same exchange/deadline budget |
| Body budgets | RDAP <=1 MiB decoded bytes; bootstrap <=512 KiB; reject oversized Content-Length and enforce streamed limits even without it |
| Parser budgets | Depth <=32, bounded strings/arrays/entities; apply limits even to skipped unknown fields; malformed UTF-8/JSON is not success |
| Refresh / retry | No automatic polling; respect Retry-After before manual retry; an expiry requires another explicit action |

HTTP mapping: 200 + valid expected domain object -> success; valid but limited
fields remain qualified data, not fabricated values. 400 -> query rejected;
401/403 -> access restricted; 404 -> no registration object for this exact
query; 429 -> rate limited with Retry-After; 5xx -> service error. Distinguish
offline/network/DNS, timeout, TLS/security failure, unsupported bootstrap,
invalid/oversized response, blocked redirect and network changed. Cancellation
propagates as cancellation, not a successful or saved lookup.
[RDAP HTTP behavior](https://www.rfc-editor.org/rfc/rfc7480.html)

Candidate models: `DomainRegistrationRequest`, `DomainRegistrationResult`,
`RegistrationStatus`, `RdapServiceInfo`, `RegistrationEvent`, `RegistrarInfo`,
`RegistrationNotice`. Result carries entered/display/ASCII name, source URL,
query times/duration, protocol, typed status and limitations; optional registry
handle, registrar, nameservers, statuses, dated events, DNSSEC and notices.
Validate response object/name against the request. Missing/redacted/unsupported
fields stay distinguishable. Do not infer registrant identity, guaranteed
expiry/renewal or trusted ownership from public fields.
[RDAP response model](https://www.rfc-editor.org/rfc/rfc9083.html)

Recommend an explicitly reviewed streaming JSON reader rather than a third
hand-written general parser or copying the private History reader. Moshi's
streaming API is a candidate; its project uses Apache-2.0, but **version,
transitive dependencies, advisories, size and Android/JDK compatibility have
not been audited or approved here**. Prefer no reflection/codegen requirement
for a small allowlisted mapping. If new production dependencies are declined,
evaluate a bounded platform JSON adapter with real host-test support first;
Android stub `org.json` under `isReturnDefaultValues` is not a parser pass.
[Moshi project](https://github.com/square/moshi),
[license](https://raw.githubusercontent.com/square/moshi/master/LICENSE.txt)

### 5.4 Endpoint security, privacy and WHOIS policy

- Endpoint policy only accepts HTTPS public RDAP authorities from the reviewed
  bootstrap/approved redirect list. Reject credentials, unsafe ports, literal
  loopback/link-local/private/ULA/CGNAT/multicast/special-use destinations and
  public-looking hostnames resolving to disallowed addresses. Recheck each
  redirect, detect loops and forbid HTTPS-to-HTTP. Do not follow a registrar
  link merely because it appears in JSON. An unapproved redirect returns an
  explicit limited result, not a lower-security fallback.
- Check actual address selection to prevent a validate-then-re-resolve gap on
  direct paths. Reuse cancellable system DNS transport where appropriate,
  not DNS-feature UseCases that save History. Monitor the shared network
  fingerprint; cancel DNS/Call/body reads and reject late generations on
  change. A coroutine timeout around blocking `InetAddress` alone does not
  prove resolver cleanup. [Android DNS API](https://developer.android.com/reference/android/net/DnsResolver)
- Respect the existing system proxy/VPN context; do not silently bypass it.
  Direct-path address enforcement must not be claimed to prove the upstream
  IP behind an HTTP/PAC proxy. Validate URI authority and system TLS identity
  regardless; expose the route limitation and keep proxy identities out of logs.
- User disclosure before the first request: the authoritative registry/service
  and any approved redirect/proxy can observe the queried domain and connection
  metadata/IP. IANA bootstrap refresh is also an external request. Do not send
  LAN lists, reports, SSID/BSSID or device identifiers. No automatic raw
  response logging, cloud uploads, account, contact-email harvesting or lookup
  History. In-memory results may contain public-but-personal data: minimize
  entity fields and show notices without rendering active HTML.
- Review actual endpoints, retention, local cache, query disclosure and current
  policy/in-app/Play Data Safety implications **before networking implementation
  acceptance/release**. This document is not a legal/Data Safety certification
  or authorization to change/deploy policy or Console declarations.
- Recommend **RDAP-only execution initially; WHOIS fallback disabled unless
  its separate gate is approved**. This follows the accepted conditional
  fallback scope, not a silent replacement with a different feature. ICANN
  made RDAP the definitive gTLD registration source in January 2025; that does
  not promise all ccTLD coverage or every old WHOIS server has disappeared.
  [ICANN transition](https://www.icann.org/en/announcements/details/icann-update-launching-rdap-sunsetting-whois-27-01-2025-en)
- If later approved, WHOIS is an **explicit** fallback only for a reviewed
  unsupported RDAP/TLD service and registry allowlist, never to evade 403/429,
  TLS validation, blocked endpoints or cancellation. It sends a domain plus
  CRLF to TCP43, has no protocol confidentiality/integrity guarantee and no
  universal charset. Require disclosure/confirmation, bounded owned socket
  and response, cancellation, no arbitrary referrals and per-service encoding
  evidence. Reuse socket ownership, not `TcpPortChecker` (which closes its
  successful connection before a WHOIS exchange).
  [WHOIS protocol/security](https://www.rfc-editor.org/rfc/rfc3912.html)

### 5.5 Tests and acceptance

- Offline fixtures first: IDN/Chinese, mixed case/root dot, invalid labels,
  malformed punycode, credentials/URL/IP/local inputs, suffix-boundary attacks,
  `.co.uk` and arbitrary subdomains. No DNS request just to validate input.
- Bootstrap: absent/HTTP-only entry, overlapping suffixes, bad update, stale
  offline cache, equivalent bases. HTTP fixtures: 200/redacted/missing fields,
  wrong object/name, 400/403/404/429/5xx, invalid charset/JSON, huge/chunked/
  compressed body, nested unknown fields, redirect loop/downgrade/private
  DNS-rebinding/IPv4-mapped IPv6, slow DNS/body and timeout/cancel/network change.
- Assert one in-flight request, closed resources, no auto retries, no fallback
  after access/security/rate-limit failure, no query/raw contacts in logs and
  no automatic lookup on entry/recreation or from History.
- Android 12/13/16 compatibility: existing system TLS, IDNA, HTTP cancellation,
  locale, VPN/proxy, offline and network switching. Use real devices when
  available; document emulator vs device and Not Tested separately. Do not
  use a live registry as a deterministic unit-test server or load-test it.
- Final controlled smoke uses explicit public test-domain queries only after
  maintainer endpoint/privacy approval. Record source/time, not a universal
  availability/coverage claim. WHOIS needs an additional explicit gate.

## 6. B4 — Website/TLS exports from existing evidence

### 6.1 What can actually be reused

`WebDiagnosticsHistorySnapshotResolver` restores schema **1** payloads for
`TLS_CHECK` and `WEBSITE_DIAGNOSTIC` into `RestoredWebDiagnosticsHistory`.
`SavedWebDiagnosticsHistoryViewModel` depends only on HistoryRepository; it
does not probe or analyze. Preserve that boundary, malformed/unknown-version
unavailable behavior and exact History ID. Live ViewModels save at most one
eligible completed snapshot; export must not invoke their start/save path.

Stored Website DNS evidence contains candidate addresses, status, duration and
failure/Fake-IP facts; restore sets its full `DnsLookupResult` to null. **Do not
export invented raw records, TTL or actual responding DNS server, or re-query
to fill them in.** TLS `PresentedCertificate` stores subject, issuer, SANs,
validity and self-signed evidence, not DER/PEM, serial, certificate fingerprints
or public-key parameters. Export only what is present. No new Core collection
is justified just to make a richer-looking report.

Website serialization already drops query/fragment/userinfo from display URLs
and Location, but retains paths, typed finding arguments and selected response
headers. "Already redacted" is **not** a sufficient export privacy policy.
Do not rewrite saved schema-1 JSON to implement export redaction.

### 6.2 Projection and shared delivery design

`live completed snapshot OR exact restored snapshot -> frozen EN/zh context
-> allowlisted redacted export projection -> Copy / TXT / Markdown / PDF
-> existing app-owned user-directed delivery`

- Add pure, feature-specific `WebDiagnosticExportMapper` / `TlsExportMapper`
  accepting only snapshots and a captured localization context. They receive
  no Engine, analyzer, network or repository-write dependency. Capture source
  kind, saved ID or live run ID, observation time and redaction policy version;
  export time is a separate label, not a fabricated new observation timestamp.
- Recommend a small neutral `core:reporting` extraction for format metadata,
  frozen export-document blocks, Markdown escaping, PDF wrapping/pagination
  and rendering. Keep tool facts/mapping in their owning feature and SAF/share
  in the app. Do not make `feature:webdiagnostics` depend on `feature:report`
  or force its snapshots into an Automatic Diagnosis model. Confirm this small
  extraction before coding; prove existing automatic-report output unchanged
  before adding web content. Do not build a general plugin/report framework.
- Reuse TextExportViewModel's frozen bytes, correlation, single-flight IO and
  process-death expiry; immutable cache + FileProvider/ClipData/read grants.
  Generalize PDF delivery in a separate tested slice: off-Main writes/render
  work as applicable, immutable PDF cache rather than deleting older shares,
  and no Activity retained by ongoing IO. The current PDF implementation is
  **not** already identical to the safer Stage A text path.
- TXT `text/plain`, Markdown `text/markdown`, PDF `application/pdf`; generic
  safe timestamp/UUID filenames without targets, query strings or private host
  names. Validate MIME/extension and bounded UTF-8/PDF output. Use typed blocks
  for headings/facts, escape all untrusted data, forbid injected remote images
  or active HTML. Reuse native Android PDF/CJK wrapping; no new PDF SDK needed.
- Add the same export actions to completed live and available saved results;
  none while loading/unavailable or before a stable result exists. Export
  failure/cancel does not change the check outcome. A deleted report must not
  become a live diagnosis. No auto save, automatic recipient or upload.

### 6.3 Proposed default redaction policy — confirm before UI integration

| Field | Default exported projection |
| --- | --- |
| Public user-selected domain/port, stage outcomes/timings, HTTP status, TLS protocol/cipher/ALPN, trust and hostname result | Preserve observed values and uncertainty, bounded/localized |
| URL userinfo, query/fragment, non-root path, Location target path | Omit credentials; remove query/fragment and replace path with an explicit redaction marker; preserve safe scheme/public authority/port and redirect stage relationship |
| Local/private/link-local/ULA/CGNAT address, local hostnames, source device IP, gateway/DNS, interface, SSID/BSSID, proxy/PAC/Private DNS server names | Mask/omit identifiers by default; preserve relevant boolean route/context and mark redacted rather than unavailable |
| Network fingerprint, raw input, arbitrary exception/log text, free-form finding arguments | Never dump generically; map only allowlisted typed fields through the same redaction policy |
| Header evidence | Preserve status/protocol and safe bounded Content-Type; omit raw Server/Via/other free text by default; Location uses URL policy; no Cookie/Authorization fields or response body |
| Certificate | Preserve validity dates/status, presented chain length, trust/hostname outcomes; omit raw DN and full extra SAN list by default, since they can contain unqueried/private identities. Only the already allowed queried public host may be referenced. Never invent fingerprint/DER or retrieve a new chain. |

Use an explicit `redacted` marker distinct from "not measured". A safety-focused
partial/failed export must retain the original failed/unknown status. Do not
rewrite findings or collapse direct TLS evidence and actual HTTP proxy/PAC/VPN
routes into one claimed path. No full-unredacted mode by default in this slice;
such an option needs a separate privacy/UX decision. Scan every output surface
(title, file metadata, paragraphs, redirects, findings, PDF and share preview),
not just URL display strings. Redaction does not make an artifact anonymous;
keep the deliberate-share warning and do not change policy publication here.
