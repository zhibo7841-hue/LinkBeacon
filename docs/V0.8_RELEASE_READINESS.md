## TLS History Contract

- Stable type: `TLS_CHECK`.
- Snapshot schema version: 1.
- One completed TLS check creates at most one History record.
- Network-changed terminal results are not persisted as completed records.
- Restoring the record reads the immutable snapshot and does not repeat the
  connection or re-run analysis.

## Website History Contract

- Stable type: `WEBSITE_DIAGNOSTIC`.
- Snapshot schema version: 1.
- One completed Website Diagnostics run creates at most one History record.
- Stopped and network-changed terminal results are not persisted as completed
  records.
- Restoring the record reads the immutable snapshot and does not repeat DNS,
  TCP, TLS, or HTTP activity and does not re-run analysis.

Malformed, unsupported, and legacy History records remain isolated by their
existing type/schema-aware presentation paths; the database schema is not
changed.

## Privacy and Redaction

The v0.8 paths remain local-first and user-initiated. History redacts URL user
information, query values, and fragments, uses a no-cookie client, does not add
authorization headers, and excludes sensitive response headers such as
`Set-Cookie`. No TLS or Website result is uploaded by LinkBeacon.

Opening a saved result is a read-only presentation operation. It neither
repeats network traffic nor silently produces a new interpretation from live
network state.

## SSL/TLS Semantics Audit

The TLS path uses the Android system trust configuration and hostname
verification. It reports the observed handshake, trust result, certificate
chain, names, validity, negotiated protocol, timing, and typed failure evidence.
It does not claim certificate pinning status, enumerate every supported cipher,
assign a security score, scan for vulnerabilities, or prove a server-wide
outage from one connection attempt.

Cancellation and active-network change remain explicit terminal paths. VPN is
presented as network context and does not automatically make the result a
failure.

## Website Staged Semantics Audit

Website Diagnostics retains its staged normalization, DNS, TCP, direct TLS,
and HTTPS evidence flow. It keeps completed evidence when a later stage cannot
finish and uses conservative typed findings rather than one absolute root-cause
claim.

Proxy/VPN/Private-DNS/Fake-IP observations remain context. A Fake-IP address is
not automatically classified as DNS failure. Direct TLS evidence is kept
separate from proxy-aware HTTP transport evidence, so a successful HTTP path
does not falsely claim that a direct TLS path succeeded.
